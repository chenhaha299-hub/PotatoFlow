# PotatoFlow workflows

1. Discussion to project

3. Project tree to schedule

## 1. Discussion to project

Extract four layers:

1. **Facts**: inventory, resources, commitments, deadlines, existing assets.
2. **Intent**: why the user wants the project and what outcome matters.
3. **Constraints**: time, money, confidentiality, dependencies, skills.
4. **Unknowns**: decisions or evidence still needed.

Turn these into one project objective and observable success criteria. Keep assumptions explicit.

## 2. Document to project tree

Build this hierarchy:

```text
Project
├─ Milestone
│  ├─ Task
│  └─ Task
└─ Milestone
   └─ Task
```

A milestone describes a result. A task describes an action that one person can finish and verify.

Avoid copying document headings directly when they are only subject areas such as "marketing" or "AI". Rewrite them as outcomes such as "complete the first content test and collect comparable data".

## 3. Project tree to schedule

Schedule in dependency order.

- Detail the next 1-2 weeks.
- Keep later dates tentative.
- Do not fill every available hour.
- Group similar production work when batching reduces setup cost.
- Give each task a minimum acceptable outcome.
- Mark external waiting time explicitly.

Before writing a large schedule, show:

- daily workload,
- task dependencies,
- assumptions about available time,
- tasks intentionally left in backlog.

## 4. Task-context problem solving

Use the stored context in this order:

1. project objective and constraints,
2. task objective and acceptance criteria,
3. current status and history,
4. issue statement and attempts,
5. related dependencies.

Respond with:

- likely cause,
- evidence and uncertainty,
- smallest next test,
- exact steps,
- success/failure signals,
- effect on the remaining plan.

## 5. Review and replanning

Do not equate activity with progress. Review outcomes against acceptance criteria.

Produce:

- completed outcomes,
- incomplete or blocked work,
- new evidence,
- invalidated assumptions,
- lessons worth retaining,
- schedule changes requiring confirmation,
- content or open-source artifacts that emerged from real work.
